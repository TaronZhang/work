# 失败处置闭环记录

本文件记录 bid_checker 在 LLM 调用失败、JSON 解析失败或网络异常时的触发条件、降级策略、人工介入阈值、接管人、通知方式和审批结果。与当前代码的单轮调用和保守降级逻辑完全一致，不包含未实现的自动重试或指数退避逻辑。

## 一、代码实现状态总览

| 项 | 说明 |
|----|------|
| 自动重试/指数退避 | 未实现 |
| 调用方式 | 同步 HTTP 单轮调用，无重试循环 |
| 错误处理模式 | try-except 单轮调用，失败时走保守降级逻辑 |
| 代码位置 | src/ai_filter.py 的 filter_tender_requirements() 和 analyze_comparison_segments() |

## 二、失败类型与触发条件

### 2.1 LLM 调用失败

| 项 | 说明 |
|----|------|
| 触发条件 | OpenAI SDK 抛出异常（模型不可用、API Key 无效、请求超时、请求体超限等） |
| 捕获位置 | src/ai_filter.py 第 196 行（事前过滤）、第 308 行（段分析） |
| 异常类型 | Exception（宽口径捕获，覆盖 OpenAIAPIError、Timeout、RateLimitError 等） |
| 触发示例 | API Key 过期、模型名称错误、并发超限、AI Gateway 服务不可用 |

### 2.2 JSON 解析失败

| 项 | 说明 |
|----|------|
| 触发条件 | LLM 返回内容无法解析为有效 JSON 数组 |
| 捕获位置 | src/ai_filter.py 第 386-388 行（_parse_filter_response）、第 415-416 行（_parse_segment_analysis） |
| 异常类型 | json.JSONDecodeError 或正则匹配失败（re.search 返回 None） |
| 触发示例 | LLM 返回自然语言而非 JSON、JSON 格式不完整、返回空字符串 |

### 2.3 网络异常

| 项 | 说明 |
|----|------|
| 触发条件 | HTTP 请求阶段发生网络层错误（DNS 解析失败、TCP 连接超时、连接被拒绝等） |
| 捕获位置 | 同 LLM 调用失败（OpenAI SDK 在网络层抛出异常，被同一 try-except 捕获） |
| 异常类型 | httpx.ConnectError、httpx.TimeoutException 等（被 Exception 捕获） |
| 触发示例 | AI Gateway 网络不通、代理配置错误、DNS 无法解析 |

## 三、降级策略

### 3.1 事前过滤失败降级

| 项 | 说明 |
|----|------|
| 降级触发 | filter_tender_requirements() 内部 LLM 调用或 JSON 解析失败 |
| 降级行为 | 失败批次的段落全部标记为 substantive（实质性内容），is_requirement = false |
| 降级结果 | 过滤后文本 = 原始文本（不过滤），后续比对使用完整招标文件 |
| 影响方向 | 重复率偏高（未移除格式要求等非实质性内容），偏保守 |
| 安全性 | 不遗漏任何匹配段，安全性不受影响 |
| 代码位置 | src/ai_filter.py 第 196-203 行 |

代码片段：
```python
except Exception as e:
    for p in batch:
        all_annotations.append(AnnotatedParagraph(
            text=p,
            category='substantive',
            is_requirement=False,
            reason=f'LLM 调用失败: {str(e)}',
        ))
```

CLI 层面降级（cli/main.py 第 234-235 行）：
```python
except Exception as e:

```

## 四、人工介入流程

### 4.1 人工重跑阈值

| 触发条件 | 人工重跑阈值 | 说明 |
|---------|------------|------|
| 单条命令 LLM 调用失败 | 立即重跑 | 售前工程师全程值守，单次比对耗时短（5-10 分钟），重跑成本低 |
| 连续 2 条命令失败 | 检查环境 | 检查网络连接、API Key 有效性、AI Gateway 服务状态 |
| 连续 3 条命令失败 | 上报经理 | 售前技术工程师上报售前技术经理，评估是否全量人工复核 |
| AI Gateway 服务不可用 | 全量人工复核 | 放弃 AI 分析，仅使用快速模式结果 + 人工全量复核 |

## 六、设计说明

### 6.1 未实现自动重试的原因

1. 招投标审查场景对准确性要求高，宁可偏保守也不能漏报
2. 降级策略天然安全：失败则全部标记为重复，不会漏过任何可疑内容
3. 运行时有人工值守，出现异常可快速手动介入
4. 单次比对耗时短（5-10 分钟），重跑成本低，人工重跑即可

### 6.2 与当前代码的一致性

| 本文件描述 | 代码实现 | 一致性 |
|-----------|---------|--------|
| 单轮调用，无自动重试 | src/ai_filter.py 中 client.chat.completions.create() 无循环/重试 | 一致 |
| 事前过滤失败 → 保留原始文本 | 第 196-203 行 except 块标记为 substantive | 一致 |
| 段分析失败 → 全部标记为实际重复 | 第 294-305 行和第 308-319 行 except 块 | 一致 |
| Web API 失败 → 返回快速模式 + 警告 | routes.py 第 262-271 行 except 块 | 一致 |
| CLI 失败 → 使用原始文本继续 | cli/main.py 第 234-235 行 except 块 | 一致 |
| 无指数退避 | 代码中无 tenacity、无 backoff、无 retry 装饰器 | 一致 |

### 6.3 后续改进方向

如需要自动重试能力，可在 src/ai_filter.py 中引入 tenacity 库或手写指数退避逻辑，对 client.chat.completions.create() 进行包装。当前版本未实现此能力，本文件如实记录。
